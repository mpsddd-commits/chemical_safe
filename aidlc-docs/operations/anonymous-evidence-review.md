# 검토 — 생성기는 근거가 어느 물질 것인지 모른다 (C13)

**일자** 2026-09-08
**발단** C11(문장별 검증 임계)을 파다가 전제가 두 번 틀린 것을 알았다.
**상태** 원인 특정 완료, 결정 대기

---

## 1. 전제가 두 번 틀렸다

**첫 번째.** C11 은 "검증 임계가 경계선에 있다"고 적었다. 그런데
`app/rag/verifier.py` 는 LLM 이 `supported`/`unsupported` 를 이진 판정한다.
**조정할 임계가 없다.** 임계를 낮추자는 처방은 애초에 실행 불가능했다.

**두 번째.** "검증기가 맞는 답을 쳐낸다"고 읽고 있었다. 거부 경로가 문장을
저장하지 않아 확인할 수 없었기 때문이다(그 자체가 결함이었고 먼저 고쳤다).
저장하고 보니 sub-06 의 걸러진 문장은 이것이다:

```
"제공된 근거에는 암모니아가 눈에 들어갔을 때 발생하는 손상에 대한
 정보가 없습니다."          verdict=unsupported, removed=true
```

**생성기가 답하기를 거절한 것**이고, 검증기는 그 메타 문장을 옳게 걸러냈다.
검증기는 처음부터 제 일을 하고 있었다.

---

## 2. 그런데 근거는 거기 있었다

sub-06 의 정답 근거는 암모니아(4957) `substance_eye` 이고, 실행 609 에서
**Recall@5 = 1.000** 이다. 청크 17518 의 원문:

```
eyeball: ·눈에 소량은 영구적은 손상을 일으킬 것임
·또한 동상을 일으킬 것임
·홍반. 통증. 심한 깊은 화상
```

골든셋의 정답 항목 세 개가 그대로 들어 있다. 검색은 성공했다.

---

## 3. 원인 — 프롬프트가 빠뜨림으로써 거짓말한다

`assembler.for_answer()` 는 근거를 이렇게 싼다:

```
<evidence id="..." title="..." section="...">본문</evidence>
```

`title` 은 `document.title` 이다. 그리고:

```
doc_type   문서  제목없음
substance   49      49
incident    12      12
law          9       9
msds        27       0
```

**물질레코드·사고·법령은 제목이 전부 비어 있다.** 그래서 sub-06 에서
생성기가 실제로 받은 상위 5는 이랬다:

```
<evidence title="" section="substance_eye">eyeball: ·눈에 접촉 시, 심한 자극과 화상을…
<evidence title="" section="substance_eye">eyeball: ·눈 자극을 일으킬 수 있음…
<evidence title="" section="substance_eye">eyeball: ·심한 눈 자극과 손상을…
<evidence title="" section="substance_eye">eyeball: ·눈에 소량은 영구적은 손상을…   ← 암모니아
<evidence title="" section="substance_eye">…
```

**이름 없는 눈 손상 설명 다섯 개.** 넷은 다른 물질(테트라브로모에테인·황산·
2-메틸-1-페닐-2-프로판올…) 것이다. 질문은 암모니아를 묻는다. 어느 것이
암모니아인지 알 방법이 프롬프트 안에 없다.

생성기는 추측하지 않고 "정보가 없다"고 답했다. **옳게 행동한 것이다.**
안전 도메인에서 이름 없는 다섯 개 중 하나를 골라 암모니아라고 답하는 쪽이
훨씬 나쁘다.

### 이미 알고 있던 사실이었다
`keyword_index.py` 주석이 2026-09-01 부터 이렇게 적고 있다:

> A substance record's chunks never contain the substance's name: the 황산
> inhale chunk reads "·심각한 기도 자극..." and the name lives only in the
> master.

이 사실을 **검색 계층에는 적용했고**(BR-65a: 이름 → CAS → 정확일치),
**생성 계층에는 적용하지 않았다.** 검색은 이름 없는 청크를 찾아내도록
고쳐졌지만, 생성기는 여전히 이름 없는 청크를 받는다.

---

## 4. 이것이 설명하는 것들

- **왜 뒤집히는가**: 상위 5에 제목 있는 MSDS 가 섞이면 답하고, 이름 없는
  물질레코드가 지배하면 거절한다. 코퍼스와 순위에 따라 갈린다.
- **왜 MSDS 15건 추가가 물질 질문을 나쁘게 했는가**: 같은 섹션 경쟁자가 늘었다.
- **왜 검색 지표는 완벽한데 답변이 실패하는가**: 검색은 정말로 맞는 청크를
  찾았다. 생성기가 그것을 구별하지 못할 뿐이다.
- **D2 가 왜 있었는지**: `meta.substance_names` 는 1,954청크 전부 빈 배열이다.
  이 필드는 정확히 이 문제를 위해 만들어졌고 채워진 적이 없다.

---

## 5. 선택지

### (a) 물질레코드에 제목을 채운다
`document.title` 을 `암모니아 (Ammonia)` 형태로 세운다.

| | |
|---|---|
| 이득 | 프롬프트가 이미 `title` 을 넣으므로 **코드 변경이 0**이다. 인용 화면도 함께 좋아진다 — 지금 사용자도 이름 없는 인용을 본다 |
| 대가 | 데이터 변경이다. 재수집·재색인 없이 `UPDATE` 로 되지만, 어댑터가 다음 수집에서 다시 비우면 원위치다 — 어댑터도 함께 고쳐야 한다 |
| 범위 | 사고 12·법령 9도 같은 상태다. 물질만 고칠지 셋 다 고칠지 정해야 한다 |

### (b) 조립기가 물질명을 붙인다
`for_answer()` 가 `document_substance` 를 타 물질명을 채운다.

| | |
|---|---|
| 이득 | 데이터를 안 바꾼다 |
| 대가 | 조립기가 DB 를 더 읽는다(NFR-2 예산). 인용 화면은 여전히 이름이 없다 — **같은 결함의 절반만 고친다** |

### (c) `meta.substance_names` 를 채운다 (D2)
색인 시점에 청크 메타에 물질명을 넣는다.

| | |
|---|---|
| 이득 | 검색·생성·인용이 전부 같은 출처를 쓴다. D2 가 처분 대기인 이유가 사라진다 |
| 대가 | **전체 재색인이 필요하다**(약 35분). 그리고 기준선 609 의 코퍼스 지문이 바뀐다 |

### (d) 현행 유지
| | |
|---|---|
| 이득 | 없음 |
| 대가 | 물질 질문이 상위 5의 구성에 따라 답하거나 거절한다. **오거부율이 계속 흔들리고**, 그 흔들림을 노이즈로 오독하게 된다 |

---

## 6. 권고

**(a) 를 먼저.** 코드 변경 0이고, 프롬프트와 인용 화면을 **동시에** 고치며,
되돌리기 쉽다. 어댑터가 다음 수집에서 제목을 세우도록 같이 고친다.

(c) 는 옳은 종착지이되 지금은 아니다 — 전체 재색인이 기준선 609 의 코퍼스를
바꾸고, 방금 이틀을 들여 세운 기준선이다. (a) 로 효과를 먼저 확인하고,
그 값이 크면 (c) 를 계획해서 한다.

(b) 는 권하지 않는다. 인용 화면의 이름 없음을 그대로 남기므로 같은 결함을
두 곳 중 한 곳만 고치는 셈이다.

**측정 방법**: (a) 적용 후 sub-06·msds-03·sub-04 를 각 3회 질의한다.
심판을 부르지 않으므로 할당량이 들지 않는다. 그다음 `--retrieval-only` 로
검색이 안 변한 것을 확인하고(변할 이유가 없다), `--full` 은 그 뒤에 잰다.
