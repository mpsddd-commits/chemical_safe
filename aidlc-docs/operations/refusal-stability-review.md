# 검토 — 거부 경계가 실행마다 흔들린다 (백로그 C8)

**일자** 2026-09-06
**발단** 실행 387 과 549 의 정답률을 비교하다 분모가 다른 것을 발견했다.
두 실행 모두 답변형 1건이 거부됐는데(오거부 0.040 동일) **그 1건이 다른
문항이었다** — 387 은 sub-06, 549 는 law-05.
**상태** 검토 — 원인 특정, 크기 미측정, 결정 대기

---

## 1. 무엇을 보았나

`refused_unsupported` 는 2단계 검증이 **모든 문장을 걷어냈다**는 뜻이다(BR-87).
답변은 생성됐고, 문장마다 근거 대조를 받았고, 하나도 통과하지 못한 것이다.
그 문항은 심판을 받지 않으므로 **정답률·충실도의 분모에서 빠진다.**

실제 `--full` 실행 7건(측정용·테스트용 제외):

```
실행   상태        거부된 답변형   어느 문항
 10   succeeded        1        msds-01
 17   succeeded        0        —
 26   succeeded        0        —
221   succeeded        2        sub-04, sub-06
276   succeeded        1        sub-06
387   succeeded        1        sub-06
549   succeeded        1        law-05
```

개수도 대상도 움직인다. sub-06 은 221·276·387 세 번 연속 거부됐다가 549 에서
빠졌고, law-05 는 549 에서 처음 나타났다.

---

## 2. 원인 — 샘플링이다

```
grep -rn "temperature" app/ --include=*.py   →  없음
```

`llm_gemini.py` 의 `_config()` 는 `system_instruction` 과 `response_schema` 만
설정하고 **온도를 지정하지 않는다.** 제공자 기본값이 적용되므로 생성도 검증도
탐욕적(greedy)이 아니라 표집이다. 같은 질문·같은 근거라도 답변 문장이 달라지고,
그 문장들이 **전부** 검증에 떨어지는지는 경계선에서 동전 던지기가 된다.

### 코드 변경으로는 설명되지 않는다
387(`03bab957bade`) → 549(`a06337a6a809`) 사이의 변경은 B3 역할, B1/B2/B2a 인증,
D4 줄바꿈, C7 심판 근거 중복 제거, nav 노출이다. **생성기와 검증기를 건드린
것은 하나도 없다.** C7 은 *심판*이 보는 근거만 바꿨다.

즉 이 뒤집힘은 코드의 효과가 아니라 **같은 코드가 두 번 다르게 답한 것**이다.

---

## 3. 왜 문제인가 — 가드의 허용오차와 만난다

```
answer.accuracy         허용 0.05      문항 1개 = 1/24 = 0.042
judge.faithfulness      허용 0.05      문항 1개 = 0.042
refusal.false_refusal   허용 0.05      문항 1개 = 1/25 = 0.040
```

**한 문항이 흔들리면 허용오차 안(0.042 < 0.05)이고, 두 문항이면 발화한다
(0.083 > 0.05).** 이것은 계산된 여유가 아니라 우연이다.

`reporter.py` 의 주석이 이미 그렇게 말하고 있다:

> Provisional until the first `--full` run produces a baseline — an unmeasured
> threshold is a guess, and this file says so rather than presenting these as
> calibrated.

**이제 `--full` 실행이 7건 있다.** 그때의 "미측정"이 지금은 부분적으로 측정됐고,
추측이었던 값을 근거로 다시 볼 수 있게 됐다.

### 오늘 실제로 오독할 뻔했다
정답률 1.000 → 0.958 을 보고 "C7 의 대가"로 읽을 뻔했다. 분모를 세어 보고서야
**겹치되 같지 않은 두 집합**을 비교하고 있었다는 것을 알았다. 지표가 같은 이름을
달고 있어도 같은 것을 재고 있다는 뜻이 아니다.

---

## 4. 아직 측정하지 못한 것 — 정직하게

**흔들림의 크기를 모른다.** 깨끗한 관측은 **한 쌍뿐**이다(387 vs 549: 생성기·
검증기 코드 불변, 한 문항 이동). 나머지 실행들은 코드나 코퍼스가 함께 달라져
노이즈만 떼어 낼 수 없다.

n=1 로는 "흔들린다"까지만 말할 수 있고 "얼마나"는 말할 수 없다. 표준편차를
구하려면 **같은 코드로 `--full` 을 여러 번** 돌려야 하고, 한 번이 심판 25콜
(일일 한도 20)이라 **한 번당 하루**다.

싼 대안이 있는지도 살펴야 한다: 거부는 *답변 모델*(`gemini-3.1-flash-lite`,
한도가 심판보다 훨씬 높다)의 산물이고 심판과 무관하다. 심판 없이 답변 경로만
반복하는 수단이 있으면 하루에 여러 번 잴 수 있다 — 지금 그런 CLI 는 없다.

## 5. 선택지

### (a) 생성·검증 온도를 0으로 고정한다
| | |
|---|---|
| 이득 | 같은 질문에 같은 답. **안전 도메인에서 재현성은 그 자체로 값이다** — 감사 가능성이 생기고, 지표가 노이즈 대신 변화를 잰다 |
| 대가 | 온도 0 이 비트 단위 결정성을 보장하지는 않는다(제공자 구현에 달렸다). 답변이 더 단조로워질 수 있고, 그 영향은 미측정이다 |
| 규모 | `_config()` 에 한 줄. 되돌리기 쉽다 |

### (b) 허용오차를 측정된 노이즈로 재교정한다
| | |
|---|---|
| 이득 | 가드가 노이즈에 발화하지 않는다. `reporter.py` 주석이 예고한 바로 그 작업이다 |
| 대가 | **노이즈를 아직 모른다**(4절). 재려면 같은 코드로 여러 번 완주해야 하고 하루씩 든다 |

### (c) 경계선 문항을 반복 측정해 다수결한다
| | |
|---|---|
| 이득 | 지표가 안정된다 |
| 대가 | 비용이 배로 든다. 무료 티어에서 `--full` 이 이미 하루인데 3회 반복이면 사흘이다 |

### (d) 지표에 노이즈 폭을 함께 표시한다
| | |
|---|---|
| 이득 | 읽는 사람이 0.042 짜리 차이를 신호로 오독하지 않는다. 오늘 내가 오독할 뻔한 것이 이것이다 |
| 대가 | 폭을 알아야 표시할 수 있다 — (b)와 같은 선행조건 |

### (e) 현행 유지
| | |
|---|---|
| 이득 | 아무것도 안 한다 |
| 대가 | 한 문항 이동은 조용히 통과하고 두 문항이면 노이즈에 발화한다. 어느 쪽이든 가드가 무엇을 말하는지 알 수 없다 |

## 6. 권고

**(a) 를 먼저, 그다음 (b).** 순서에 이유가 있다.

1. **(a) 는 싸고 원인을 직접 건드린다.** 한 줄이고 되돌리기 쉽다. 그리고
   안전 도메인에서 "같은 질문에 같은 답"은 지표를 위한 편의가 아니라 **제품의
   성질**이다 — 사용자가 어제 받은 답과 오늘 받은 답이 다르면, 어느 쪽을 근거로
   행동해야 하는지 알 수 없다.
2. **(a) 를 하면 (b) 가 쉬워진다.** 노이즈가 줄면 남은 흔들림의 크기를 재는 데
   필요한 반복 횟수도 준다. 지금 (b) 부터 하면 큰 노이즈를 큰 허용오차로
   덮는 셈이고, 그러면 진짜 회귀도 함께 덮인다.
3. **(d) 는 (a)·(b) 뒤에 판단한다.** 폭을 모르는 채로 폭을 표시할 수는 없다.

**측정 계획**: (a) 적용 후 같은 코드로 `--full` 을 2~3회 돌려 거부 문항이
고정되는지 본다. 하루씩 걸리므로 다른 작업과 병행한다.

**다만 (a) 가 답이 아닐 수 있다는 것도 적어 둔다.** 온도 0 에서도 제공자가
같은 출력을 보장하지 않으면 흔들림은 남는다. 그때는 원인이 표집이 아니라
**검증 임계 자체가 경계선에 있다**는 뜻이고, 다른 문제가 된다.
