# 검토 — Recall@10 을 어떻게 할 것인가 (백로그 C4)

**일자** 2026-09-06
**발단** 결함 49 — `FINAL_TOP_K=5` 라 후보 목록이 5건이고, 5건짜리 목록의
Recall@10 은 이름만 다른 Recall@5 다. `reporter.aggregate()` 가 `depth<10` 이면
`None` 을 내보내므로 이 지표는 지금까지 **영구히 `--`** 였다.
**상태** 검토 — 측정 완료, 결정 대기

---

## 1. 결함 49 의 전제가 틀렸다

결함 49 는 "5건짜리 목록에서 @10 은 @5 와 같으므로 변할 수 없는 비교"라고
적었다. 그 문장은 **목록이 5건일 때** 옳다. 그러나 목록이 5건인 것은 자연법칙이
아니라 `FINAL_TOP_K` 라는 설정값이고, **깊이 10의 순위 정보는 이미 파이프라인
안에 있다.**

```
keyword_top_k 30 · vector_top_k 30 · fusion_top_k 20 · final_top_k 5
```

`query_service.retrieve()` 는 융합 결과를 **20건**까지 만든 뒤
(`[: fusion_top_k]`) `ensure_doc_type_spread(fused, final_top_k)` 로 5건으로
줄인다. 즉 6~20위의 순위는 계산돼 있고, 하류로 넘어가지 않을 뿐이다.

**Recall@10 을 재는 데 "더 검색"은 필요 없다. "이미 계산된 것을 더 관측"하면 된다.**

---

## 2. 측정했다 — 코드를 고치지 않고

`final_top_k` 는 `Settings` 필드라 환경변수로 바뀐다(`FINAL_TOP_K=10`). 빌드
지문은 파일을 해싱하므로 env 변경으로는 바뀌지 않는다 — **되돌릴 코드가 없다.**
`--retrieval-only` 는 LLM 0콜이라 몇 번을 돌려도 할당량이 줄지 않는다.

```bash
scripts/measure_recall_at_10.sh        # 실행 550·551
```

```
깊이 5    Recall@5 0.967   Recall@10 --      MRR 0.766
깊이 10   Recall@5 0.933   Recall@10 1.000   MRR 0.766
```

### 두 가지가 예상 밖이다

**① Recall@10 = 1.000.** 30문항 전부의 정답 근거가 깊이 10 안에 있다.
이 지표는 잴 수 있고, **무언가를 말한다** — "검색이 근거를 찾지 못한 적은 없다.
다만 상위 5에 못 올린 적이 있다"는 것이 그 말이다. 그것은 Recall@5 가 하지
못하는 진단이고, BR-124 가 두 지표를 함께 두려던 이유다.

**② Recall@5 가 0.967 → 0.933 으로 내려간다.** `final_top_k` 를 올리면
`ensure_doc_type_spread(fused, limit)` 의 결과가 달라져 **상위 5의 구성이
바뀐다.** 두 지표는 중첩되지 않는다.

### 문항 단위 — 제로섬이다
```
sub-02   Recall@5 0.000 → 1.000    5위로 진입
sub-06   Recall@5 1.000 → 0.000    9위로 밀림  (깊이 10 안에는 있다)
sub-07   Recall@5 1.000 → 0.000    8위로 밀림  (깊이 10 안에는 있다)
```
하나를 얻고 둘을 잃는다. law-08·09 개선 때 본 것과 같은 모양이다 — **순위
재편은 제로섬**이고 분산 규칙이 무엇을 상위로 올릴지 다시 정한다.

### 부수 발견 — 골든셋 B 결정과 닿는다
**sub-02 의 정답 근거는 깊이 10 안에 있다.** 2026-09-01 의 판단 자료는
"황산 흡입 섹션이 5위 안에 못 든다"고 적었는데, 이제 **어디에 있는지**를 안다.
E1(sub-02 골든셋 B 유지)을 재론한다면 이 사실이 새 입력이다. 근거가 없는 것과
5위 밖에 있는 것은 다른 상태다.

## 3. 긴장 — BR-115 / DD-22

```
evaluation_service.py 상단:
  "The service calls QueryService.answer() and nothing else (BR-115).
   There is no evaluation-only retrieval path... the moment the evaluated
   pipeline differs from the shipped one, the metrics describe something
   nobody runs."
```

이 규칙은 강하고 옳다. 문제는 **"융합 중간 결과를 관측하는 것"이 이 규칙을
어기는가**다.

| 어긴다고 볼 근거 | 어기지 않는다고 볼 근거 |
|---|---|
| 평가가 `answer()` 반환값 밖의 것을 읽으면, 평가만 아는 상태가 생긴다 | 관측 대상은 **같은 호출이 이미 만든 값**이다. 다른 검색을 돌리는 것이 아니다 |
| "관측"과 "경로"의 경계가 흐려지면 다음 사람이 더 밀고 들어간다 | 답변·인용·거부는 여전히 상위 5로만 결정된다. 사용자가 받는 것은 한 글자도 안 바뀐다 |

**핵심 판별**: 관측이 *제품의 동작*을 바꾸는가. 바꾸지 않으면 DD-22 가 막으려던
것("평가가 아무도 안 쓰는 것을 잰다")은 일어나지 않는다 — 오히려 반대로,
제품이 실제로 계산하는 것을 더 정확히 재게 된다.

## 4. 선택지

### (a) 지표에서 제거한다
`DEFAULT_KS` 에서 10을 빼고 `recall_at_10` 을 없앤다.

| | |
|---|---|
| 이득 | 영구히 `--` 인 열이 사라진다. 화면과 표가 정직해진다 |
| 대가 | **측정으로 반박됐다.** @10=1.000 은 실제 정보다. 지울 이유가 사라졌다 |

### (b) 융합 중간 결과를 관측한다 ← 측정이 지지하는 쪽
`retrieve()` 가 상위 5를 그대로 반환하되, 평가가 읽을 수 있도록 융합 목록의
상위 N(예: 10)을 함께 노출한다. 파이프라인의 동작은 불변.

| | |
|---|---|
| 이득 | Recall@5 를 **잃지 않고**(0.967 유지) Recall@10 을 안다. 두 지표가 처음으로 서로 다른 것을 말한다 — BR-124 의 원래 의도 |
| 대가 | `answer()` 의 반환 형태가 늘어난다. BR-115 의 경계를 어떻게 읽을지 문서로 못박아야 한다(3절) |
| 규모 | `QueryResult` 에 필드 하나, `evaluation_service` 에서 그 필드를 쓰도록 한 줄, `retrieval_metrics` 는 그대로. 재색인 불필요 |

### (c) `FINAL_TOP_K` 를 10으로 올린다
| | |
|---|---|
| 이득 | 코드 변경 0. 설정 한 줄 |
| 대가 | **Recall@5 0.967 → 0.933 (실측).** 그리고 생성기가 보는 근거가 5건에서 10건으로 늘어 **답변·비용·인용·충실도가 전부 바뀐다** — 프롬프트가 두 배가 되고, 무료 티어에서 문장당 검증 비용도 함께 는다. 지금 기준선 전체가 무효가 된다 |

### (d) 현행 유지
| | |
|---|---|
| 이득 | 아무것도 안 한다 |
| 대가 | @10 열이 영구히 `--` 로 남는다. **잴 수 있는데 안 재는 상태**이고, 결함 49 의 기록이 틀린 채로 남는다 |

## 5. 권고

**(b) 를 권한다.** 근거 셋:

1. **측정이 (a) 를 반박하고 (c) 를 비싸게 만들었다.** @10=1.000 은 정보이고,
   (c) 는 Recall@5 를 0.034 잃으며 답변 경로 전체를 바꾼다.
2. **(b) 만이 두 지표를 서로 다른 것으로 만든다.** 지금 @5 는 "상위 5에
   올렸는가", @10 은 "찾기는 했는가"를 잰다. 하나가 1.000 이고 다른 하나가
   0.967 이면 **남은 0.033 이 검색 실패가 아니라 순위 문제**라고 말해 준다 —
   그것이 다음에 무엇을 고칠지 가리킨다.
3. **제품 동작이 불변이다.** 사용자가 받는 답변·인용·거부는 한 글자도
   안 바뀐다. DD-22 가 막으려던 상황이 아니다.

다만 (b) 를 하려면 **BR-115 의 경계를 문서로 다시 그어야 한다** — "평가는 별도
검색 경로를 갖지 않는다"와 "평가는 파이프라인이 이미 만든 중간값을 관측할 수
있다"를 함께 적어야, 다음 사람이 이 틈으로 더 밀고 들어오지 않는다.

**결정하지 않는 쪽도 방어 가능하다**: @10 이 1.000 인 동안은 그 지표가
알려 주는 것이 "아직 문제 없음"뿐이다. 값이 1.000 밑으로 내려가는 날이
와야 진단으로서 값을 한다.
