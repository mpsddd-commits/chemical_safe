# 검토 — 정확일치 예산을 한 문서가 통째로 먹는다 (실행 606)

**일자** 2026-09-07
**발단** MSDS 15건을 추가(코퍼스 82 → 97 문서)한 뒤 검색이 내려갔다.
Recall@5 0.967 → 0.933 · **Recall@10 1.000 → 0.967** · MRR 0.772 → 0.751.
**상태** 원인 특정 완료, 수정 진행 중

---

## 1. 무엇을 보았나

집계만 보면 "코퍼스가 커져서 순위가 재편됐다"로 읽힌다. 실제로 이 프로젝트는
law-08·09 와 C4 에서 **순위 재편이 제로섬**임을 두 번 실측했다. 그래서 집계를
믿지 않고 문항 단위로 뺐다.

```
문항      Recall@5   Recall@10   MRR
law-02    1.000→1.000  1.000→1.000  0.250→0.333
msds-01   1.000→1.000  1.000→1.000  1.000→0.500
sub-07    1.000→1.000  1.000→1.000  0.200→1.000
sub-01    1.000→0.000  1.000→0.000  1.000→0.000   ←
```

제로섬이 아니었다. **sub-01 하나가 통째로 무너졌다.** 나머지는 오히려
개선됐다(sub-07 은 rr 0.200 → 1.000). 집계의 하락은 한 문항이 낸 것이다.

---

## 2. 원인 — 정렬 없는 LIMIT

sub-01 은 `CAS 7664-93-9 물질은 무엇인가요?` 이고 정답 근거는 물질레코드
(문서 86, `doc_type=substance`)의 `substance_identity` 다.

실행 606 이 실제로 검색한 것:

```
키워드 30건: 전부 문서 20·21 (황산 MSDS), 전부 score=1.0000 (정확일치)
             문서 86 → 없음
벡터  30건: rank 0 이 문서 86 (score 0.5139)
             문서 86 → 있음
```

`keyword_index.lookup_exact()`:

```python
stmt = select(ChunkRow.id).where(ChunkRow.meta[field].astext == term)
stmt = apply_scope(stmt, scope)
rows = self._s.execute(stmt.limit(limit)).all()   # ORDER BY 가 없다
```

문서 20 이 16청크, 문서 21 이 14청크 — **합이 정확히 30**이고 이것이
`keyword_top_k` 와 같다. 두 MSDS 가 예산을 꽉 채우고 물질레코드의 7청크는
잘려 나간다.

그리고 벡터에만 남은 청크는 RRF 에서 두 경로 모두에 있는 청크를 이길 수 없다.
**rank 0 짜리 근거가 최종 20위 밖으로 밀려난 이유가 이것이다.**

### 잠복이었다
재수집 전 두 MSDS 는 28청크였다. 2칸이 남아 물질레코드가 들어갔고 sub-01 은
1.000 이었다. **늘 2칸 차이로 아슬아슬했다.** 코퍼스 추가가 원인이 아니라
방아쇠다 — 청크가 두 개만 늘어도 같은 일이 났을 것이다.

### 정렬이 없다는 것 자체가 결함이다
`ORDER BY` 없는 `LIMIT` 은 어느 30건이 남는지 정하지 않는다. 이번에는 새로
쓰인 MSDS 청크가 앞섰지만, 그것은 물리적 저장 순서이지 계약이 아니다.
**같은 질문에 같은 답이 나온다는 보장이 없는 코드**이고, 온도 0 을 고정해
재현성을 얻으려 한 결정(C8(a))과 정면으로 어긋난다.

### 결함 분류
알려진 6가지 모양 중 **④ 선택적인 것이 필수적인 것의 예산을 파괴한다**.
BR-65a(`ensure_subject_presence`)가 바로 이 상황을 막으려고 있는데, MSDS
청크들도 같은 CAS 라 `EXACT_MATCH_SCORE` 를 달고 있어 **그것들이 먼저 "주제가
존재한다"는 조건을 만족시켜 버린다.** 가드가 있는데도 통과한 이유다.

## 3. 선택지

### (a) `keyword_top_k` 를 올린다
| | |
|---|---|
| 이득 | 설정 한 줄. 코드 변경 0 |
| 대가 | **잠복을 미룰 뿐이다.** 물질 하나에 MSDS 가 세 건 붙으면 다시 넘친다. 정렬 없는 LIMIT 도 그대로다 |

### (b) 문서당 하드캡 (문서당 N개)
| | |
|---|---|
| 이득 | 한 문서가 넘치지 못한다. 이 파일에 이미 같은 어휘가 있다(`_TITLE_TIER_LIMIT`) |
| 대가 | 어느 N개인가가 문제다. `ordinal` 순이면 항상 앞쪽 섹션만 남아 **뒤쪽 섹션을 묻는 MSDS 질문이 다친다**(msds-07 저장·취급, msds-08 보호구) |

### (c) `doc_type=substance` 를 우대한다
| | |
|---|---|
| 이득 | sub-01 은 확실히 고쳐진다 |
| 대가 | 특정 유형에 특혜를 주면 **다음 질문 유형이 바뀔 때 또 특혜가 필요해진다.** 지금 고치는 것은 "물질레코드가 밀렸다"가 아니라 "한 문서가 다른 문서를 통째로 밀어낸다"이다 |

### (d) 문서 단위 라운드로빈 ← 채택
매칭 청크를 문서별로 묶고 번갈아 뽑는다: doc20[0], doc21[0], doc86[0],
doc20[1], ... `document_id` 오름차순, 문서 안에서는 `ordinal` 순으로 고정.

| | |
|---|---|
| 이득 | 한 문서가 다른 문서를 **통째로** 지우지 못한다. 유형 중립이다. 30칸·3문서면 문서 86 의 7청크가 전부 들어가고 MSDS 도 각 11~12청크를 유지한다 — (b) 의 하드캡보다 MSDS 커버리지가 덜 다친다. **결정적**이라 같은 질문에 같은 답이 나온다 |
| 대가 | `lookup_exact` 가 조금 복잡해진다. DB 에서 가져오는 행 수에 상한이 필요하다 |

## 4. 왜 골든셋을 건드리지 않는가

sub-01 은 "CAS 를 주면 그 물질이 무엇인지 답한다"는 가장 기본적인 질문이고,
정답 근거는 물질레코드가 맞다. 지표가 내려갔을 때 문항을 고치면 **지표는
회복되고 제품은 그대로 고장 나 있다.** 이 프로젝트가 다섯 번의 검색 개선을
거치며 골든셋을 한 줄도 고치지 않은 이유가 그것이다.

## 5. 결과 — (d) 적용, 실행 607

```
실행   코퍼스   코드              Recall@5   Recall@10   MRR
604    옛      f3f6b9235c8a       0.967      1.000      0.772
606    새      d85e5887484f       0.933      0.967      0.751
607    새      a0948e873252       0.967      1.000      0.762
```

**같은 코퍼스끼리인 606 → 607 은 세 지표가 모두 올랐다.** sub-01 의 융합 1위가
`chunk 17521 / doc 86 / substance_identity` — 골든셋이 지목한 바로 그 청크다.

라이브 확인: 5회 호출 결과 동일(결정성), 문서별 배분 `{20: 12, 21: 11, 86: 7}`,
순서 `doc20[0], doc21[0], doc86[0], doc20[1], ...` — 설계대로다.

단위 테스트 724 통과. 변이 검증 2건으로 새 테스트가 실제로 무언가를 잡는 것을
확인했다(라운드로빈 제거 → 3건 실패, `ORDER BY` 제거 → 1건 실패).

### 대가 — 두 문항의 MRR
```
sub-04  MRR 0.500 → 0.333    정답 근거 substance_oral   (ordinal 5)
sub-07  MRR 1.000 → 0.500    정답 근거 substance_inhale (ordinal 2)
```
Recall@5·@10 은 둘 다 1.000 유지. 물질레코드의 `ordinal 0` 은 항상
`substance_identity` 라, 정렬이 결정적이 되자 identity 가 늘 앞선다.

**606 에서 이 둘이 앞섰던 것은 실력이 아니라 우연이었다.** 같은 sub-07 이
604 에서는 0.200 이었고, 코드 한 줄 안 바뀐 채 코퍼스만 달라지자 1.000 이
되었다. 정렬 없는 LIMIT 이 주던 난수가 사라진 자리에 실제 순서가 드러난 것이다.

## 6. 이어서 드러난 것 — 경로 간 비대칭 (C10)

`_resolved_record_chunks()`(이름 해석 경로)에는 `_preferred_sections` 로 질문이
가리키는 섹션을 앞으로 올리는 장치가 있다. **`lookup_exact()`(타이핑된 CAS,
BR-38)에는 없다.**

즉 같은 질문을 **이름으로 물으면 흡입 섹션이 먼저 오고, CAS 로 물으면
identity 가 먼저 온다.** 지표 문제가 아니라 제품 동작의 비대칭이고,
예전에는 임의 순서가 그 부재를 가려 주었다.

두 경로에 같은 규칙을 적용하는 것이 이 결함의 나머지 절반이다.
