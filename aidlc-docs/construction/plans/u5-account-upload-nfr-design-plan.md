## 실측 — 이미 있는 방어

### NFR-14 비밀값 마스킹은 u1 이 만들었다

```python
# core/logging.py — BR-59·BR-60
_SECRET_PARAM  = r"(api[-_]?key|serviceKey|access[-_]?token|token|secret|password|pwd|authorization)\s*[=:]\s*…"
_SECRET_KEY_NAMES = {"password", "token", "secret", "authorization", "auth", "credentials", …}
_SECRET_KEY_SUFFIXES = ("_api_key", "_secret", "_token", "_password", "_pwd")
```

`password`·`token`·`authorization` 이 이미 잡힌다. **u5 가 확인해야 할 것은
새 경로 두 가지**다 — `Cookie:` 헤더와 argon2 해시 문자열(`$argon2id$…`).
전자는 `authorization` 패턴에 안 걸리고, 후자는 유출돼도 즉시 위험하진 않지만
로그에 남을 이유가 없다.

### 없는 것

| 없는 것 | 이 단계에서 정해야 하는가 |
|---|---|
| 레이트 리밋 · 잠금 | **예** — 로그인이 생기면 무차별 대입이 생긴다 (FQ7-1) |
| 사용자별 용량 한도 | **예** — 업로드가 생기면 디스크 고갈이 생긴다 (FQ7-2) |
| `/data/uploads` 볼륨 | **예** — compose 에 없다 (FQ7-3) |
| 인증 의존성 | **예** — `get_session()` 만 있다 (FQ7-4) |

### 성능 예산은 이 유닛에 직접 걸리지 않는다
NFR-1~3 은 질의·카드 예산이고 로그인·업로드에 대응하는 항목이 없다. NFR-4(색인
처리량 8시간/1,000종)는 색인 경로를 그대로 쓰므로(BR-142) **이미 검증된 경로**다.
→ 새 예산을 발명하지 않고, **관측 가능하게만 만든다**(FQ7-10).

# 2부. 설계 질문

## 인증 통제

### FQ7-1. 로그인 무차별 대입 방어

로그인이 생기는 순간 생기는 문제다. 지금 어떤 방어도 없다.

- **(a)** **계정별 지수 백오프** — 연속 실패 5회부터 지연(1s→2s→4s…최대 30s),
  잠금 없음 *(권장)*
- **(b)** 계정 잠금 — 5회 실패 시 15분 잠금
- **(c)** IP 기반 레이트 리밋
- **(d)** 없음 (BR-133 의 비밀번호 정책에 의존)

> *(권장 근거)*: (b)는 **공격자가 남의 계정을 잠글 수 있는** 서비스 거부 도구가 된다
> — 이메일만 알면 된다. (c)는 프록시·NAT 뒤 사용자를 함께 막고, 이 앱은 지금
> `127.0.0.1` 바인딩이라 IP 다양성 자체가 없다.
> (a)는 정당한 사용자의 오타 몇 번은 거의 방해하지 않으면서 자동화 시도의
> 처리량을 떨어뜨린다. 상태는 `user_account` 의 실패 카운터 두 컬럼이면 된다.
> (d)는 argon2 자체가 느려 초당 시도 수를 제한하긴 하지만, **그것을 방어라고
> 부르는 것은 우연에 기대는 것**이다.

[Answer]: a  *(권장안)*

### FQ7-2. 인증 의존성을 어디에 두는가

- **(a)** FastAPI 의존성 2종 — `current_user`(익명 허용, `None` 가능) ·
  `require_user`(미인증이면 로그인으로 리다이렉트) *(권장)*
- **(b)** 미들웨어에서 전역 처리
- **(c)** 라우터마다 직접 쿠키 파싱

> *(권장 근거)*: 두 종류가 필요한 이유는 BR-151 이다 — 질의·물질 화면은 익명을
> 허용하고 문서·이력은 아니다. **하나로 합치면 어느 쪽이든 틀린 기본값을 갖는다.**
> (b)는 예외 목록을 유지해야 하고, 예외 목록은 화면이 늘 때마다 잊힌다.
> (c)는 u1 이 `Scope` 를 필수 인자로 만든 이유(DD-19)를 라우터 층에서 되풀이하는 것이다.

[Answer]: a  *(권장안)*

### FQ7-3. 토큰 무효화 범위

토큰은 상태가 없다(BR-136). 로그아웃은 쿠키 삭제다.

- **(a)** **로그아웃 = 쿠키 삭제만.** 서버 측 무효화 없음 *(권장)*
- **(b)** 토큰 블랙리스트 (Redis)
- **(c)** `user_account.token_epoch` 를 두고 토큰에 실어 비교

> *(권장 근거)*: (b)·(c)는 "탈취된 토큰을 즉시 죽인다"를 얻지만, 그 대가로
> **모든 요청이 상태를 조회**하게 되고 무상태 토큰의 이점이 사라진다.
> 만료가 12시간이라 노출 창이 제한적이고, 비밀번호 변경 기능은 FR 에 없다.
> ⚠️ **탈취된 토큰은 최대 12시간 유효하다**고 문서에 적는다 — (a)를
> "무효화 지원"이라고 쓰지 않는다.

[Answer]: a  *(권장안)*

## 업로드 통제

### FQ7-4. `/data/uploads` 볼륨과 권한 (NFR-30, NFR-31)

- **(a)** **명명 볼륨 `safeenv_uploads`**, `app`·`worker` 양쪽에 마운트,
  `appuser` 소유, 퍼미션 0700 *(권장)*
- **(b)** 바인드 마운트 `./data/uploads`
- **(c)** 기존 `/data/originals` 아래에 하위 디렉터리로

> *(권장 근거)*: (c)는 **수집 원본(BR-44)과 사용자 업로드를 한 트리에 섞는다** —
> 백업·삭제·권한 정책이 서로 다른 두 종류의 데이터다.
> (b)는 호스트에 그대로 노출돼 개발에는 편하지만 사용자 파일이 리포지토리 옆에
> 놓인다. (a)는 NFR-31(볼륨 영속화)을 그대로 만족하고 컨테이너 밖에서 실수로
> 열리지 않는다. `app` 은 쓰기(업로드), `worker` 는 읽기(색인)가 필요하다.

[Answer]: a  *(권장안)*

### FQ7-5. 사용자별 저장 용량 한도

업로드가 생기면 디스크 고갈이 생긴다. 지금 한도가 없다.

- **(a)** **사용자당 총 200MB · 문서 50건** *(권장)*
- **(b)** 문서 수만 제한 (50건)
- **(c)** 전역 한도만 (디스크 사용률 감시)
- **(d)** 없음

> *(권장 근거)*: 파일당 20MB(BR-139)만 있으면 한 사용자가 파일을 반복해 올려
> 디스크를 채울 수 있고, 그러면 **다른 사용자의 업로드와 색인이 함께 멈춘다.**
> 200MB는 20MB 파일 10개 또는 평균 2MB MSDS 100건이다 — 실제 사용 규모(코퍼스
> MSDS 8건)에 비해 넉넉하다.
> (c)는 이미 찬 뒤에야 알게 되고 **누가 채웠는지 모른다.**
> 한도 초과는 업로드 거부이며 이유를 그대로 보여준다(BR-139 와 같은 태도).

[Answer]: a  *(권장안)*

### FQ7-6. 색인 실패 시 문서·파일의 상태

업로드는 성공했는데 색인이 실패할 수 있다 — u3 에서 MSDS PDF 8건 중 2건이 섹션 0
으로 끝난 것과 같은 일이 업로드에서도 일어난다.

- **(a)** **문서와 파일을 남기고 상태만 표시.** 재색인으로 재시도 가능 *(권장)*
- **(b)** 실패 시 문서·파일 자동 삭제
- **(c)** 문서는 남기고 파일은 삭제

> *(권장 근거)*: (b)는 **사용자가 올린 것을 시스템이 조용히 지우는 일**이다.
> 원인이 일시적(워커 재시작, 임베딩 모델 로딩 실패)일 수 있고, 그 경우 파일을
> 지우면 되돌릴 방법이 없다.
> (c)는 재색인이 불가능한 문서 행을 남긴다 — 있으나 마나 한 상태다.
> u1 의 `job_item` 이 이미 실패 사유를 기록하므로(FR-8) 화면에 그대로 띄운다.
> **"구조화 실패"를 숨기지 않는다**는 u3 의 태도와 같다.

[Answer]: a  *(권장안)*

### FQ7-7. 업로드 중복

같은 파일을 두 번 올리면?

- **(a)** **허용한다.** 별개 문서로 저장 *(권장)*
- **(b)** 내용 해시로 거부
- **(c)** 내용 해시로 기존 문서를 갱신

> *(권장 근거)*: u1 의 `content_hash`(BR-09)는 **수집 소스의 변경 감지**용이지
> 중복 방지용이 아니다. 사용자가 개정판을 같은 이름으로 올리는 것은 정상이고,
> 내용이 같은 파일을 두 개 올리는 것은 사용자의 자유다.
> (b)는 "왜 안 올라가는지" 설명하기 어려운 실패를 만든다. (c)는 **사용자가 지시하지
> 않은 덮어쓰기**다 — 되돌릴 수 없는 동작을 추측으로 하지 않는다.
> 용량 한도(FQ7-5)가 남용을 이미 막는다.

[Answer]: a  *(권장안)*

## 격리 검증 — 이 유닛의 중심

### FQ7-8. ⭐ 소유자 격리를 **어떻게 증명하는가**

BR-145 는 "`Scope` 는 서비스가 만든다"이고, 위험은 **어딘가에서 안 만드는 것**이다.
규칙을 적는 것과 그것이 지켜지는 것을 확인하는 것은 다르다.

- **(a)** **세 겹** — ① 두 사용자 픽스처로 교차 접근 통합 테스트
  ② `Scope(` 직접 생성을 C55 밖에서 금지하는 정적 검사
  ③ 검색 경로별 `owner_id` 필터 적용 여부 단위 테스트 *(권장)*
- **(b)** 통합 테스트만
- **(c)** 코드 리뷰로 확인

> *(권장 근거)*: 이 프로젝트는 **"테스트는 초록불인데 그 경로가 한 번도 돈 적이
> 없다"로 결함 5건**(25·39·40·46·47)을 만들었다. 격리는 그 실패가 가장 비싼
> 자리다 — 조용히 깨지고, 깨진 것을 아무도 모른다.
> ①은 실제로 새는지 보고, ②는 **새 라우터가 규칙을 우회하는 것**을 잡고,
> ③은 검색 경로(벡터·키워드·물질·이력)마다 필터가 실제로 걸리는지 본다.
> ②가 필요한 이유: ①은 **테스트가 커버하는 경로만** 본다. 새로 추가된 화면이
> `Scope(owner_id=...)` 를 직접 만들면 ①은 통과하고 ②만 잡는다.

[Answer]: a  *(권장안)*

### FQ7-9. 격리 통합 테스트의 데이터

- **(a)** **테스트가 두 계정과 각자의 문서를 만들고, 끝나면 지운다** *(권장)*
- **(b)** 공개 코퍼스에 owner_id 를 붙여 재사용
- **(c)** 별도 테스트 DB

> *(권장 근거)*: (b)는 **실코퍼스를 변조**한다 — 결함 48(통합 테스트가 청크를 지웠다)·
> 결함 53(기준선을 남겼다)과 같은 부류를 자초하는 일이다.
> (c)는 마이그레이션·시드를 이중으로 관리하게 된다.
> (a)는 자기가 만든 것만 건드리고, 정리까지 자기 책임이다. **결함 48·53 에서
> 배운 형태**다.

## 관측·운영

### FQ7-10. 인증·업로드의 관측

새 성능 예산을 만들지는 않되, 보이지 않으면 안 된다.

- **(a)** **구조화 로그에 이벤트만** — `login_succeeded`·`login_failed`(이메일 마스킹)·
  `upload_accepted`·`upload_rejected(reason)`·`isolation_denied` *(권장)*
- **(b)** (a) + 전용 메트릭 테이블
- **(c)** 기존 `job` 진행률로 충분

> *(권장 근거)*: u1 의 JSON 로거가 이미 있고 상관 ID 도 붙는다. 새 테이블(b)은
> 운영 화면이 없는 상태에서 쓰는 사람이 없다 — u4 가 `evaluation_run` 을 만든 것은
> **비교라는 명확한 소비자**가 있었기 때문이다.
> `isolation_denied` 를 넣는 이유: **격리가 실제로 막은 순간**을 볼 수 없으면
> 격리가 동작하는지 사후에 알 방법이 없다.
> ⚠️ 이메일은 로그에서 마스킹한다 — 지금 마스킹 규칙은 이메일을 모른다.

[Answer]: a  *(권장안)*

### FQ7-11. NFR-14 마스킹의 확장

- **(a)** **`cookie`·`set-cookie`·이메일·argon2 해시 패턴 추가** *(권장)*
- **(b)** 쿠키만 추가
- **(c) ** 확장 없음 (기존 패턴으로 충분)

> *(권장 근거)*: 기존 패턴은 `password`·`token`·`authorization` 을 잡지만
> **`Cookie: session=...` 은 못 잡는다** — 그 안에 JWT 가 통째로 들어 있다.
> 이메일은 비밀값은 아니지만 계정 식별자이고, 로그가 그대로 남으면 실패 로그가
> **가입자 명단**이 된다.
> argon2 해시는 유출돼도 즉시 위험하진 않지만 로그에 있을 이유가 없다.
> (c)는 "충분하다"를 확인 없이 주장하는 것이다 — 실제 로그로 확인한다.

[Answer]: a  *(권장안)*
