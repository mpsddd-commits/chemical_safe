# Business Logic Model — u3-substance-card

**유닛**: `u3-substance-card` (3/5)
**작성일**: 2026-08-26

워크플로 **W12 ~ W14**. (W1~W6 은 u1, W7~W11 은 u2)

---

## W12. 물질 마스터 투영 (결함 40, BR-33·BR-37)

**색인 경로 안에서 일어난다**(FQ4-1=A). u3 이 뒤늦게 정리하는 구조로 두면 다음
수집에서 같은 구멍이 다시 생긴다. BR-33·BR-37 은 u1 규칙이고 FR-1 로 추적된다 —
원래 있어야 했던 자리다.

```
IndexingService.index_document(ref, doc_type=substance)
   │
   ├─ … 기존 색인 (추출 → 정규화 → 구조화 → 청킹 → 임베딩 → 저장)
   │
   ├─ ★ 물질 투영                                        (BR-97)
   │     원본 payload 에서 cas_number / name_ko / name_en 을 읽는다
   │     ├─ 셋 다 없으면 → 저장하지 않는다               (BR-33)
   │     └─ SubstanceRepo.upsert(cas_number=…, name_ko=…, name_en=…)
   │           cas 기준 upsert. 재색인이 중복을 만들지 않는다  (BR-98)
   │
   ├─ ★ 동의어 등록                                       (BR-99)
   │     name_ko → term_type=name_ko
   │     name_en → term_type=name_en
   │     이명은 등록하지 않는다 — 원본에 없다
   │
   └─ ★ 문서↔물질 연결                                    (BR-37)
         relation = msds:subject / incident:mentioned / law:regulated
```

**기존 코퍼스는 재색인 1회로 채운다**(FQ4-2=A). BR-44 보존 원본에서 투영하므로
소스 재호출이 없다. BR-20a·BR-31a·BR-27a·N3 스캐너가 전부 이 경로로 배포됐다.

> **왜 전용 백필 명령을 만들지 않는가**: 경로가 하나 늘어나면 "색인은 했는데 백필을
> 안 돌렸다"는 상태가 가능해진다. 결함 40 이 정확히 그 모양이었다 — 쓰기 경로가
> 색인과 분리돼 있어서 아무도 부르지 않았다.

## W13. 물질 조회 (FR-23, FR-26)

```
[입력 문자열]
   │
   ├─ 1. 정규화 — u1 normalize() 재사용                    (BR-100)
   │       색인과 조회가 같은 정규화를 써야 한다
   │
   ├─ 2. 키 판별
   │     ├─ CAS 정규식 일치  → cas 완전일치      → 단일 결과
   │     ├─ UN 정규식 일치   → un 완전일치       → **항상 0건** (데이터 없음)
   │     └─ 그 외           → 동의어 표 조회     → 0..N 건
   │
   ├─ 3. 결과 판정                                          (BR-101)
   │     0건  → "해당 물질을 찾지 못했습니다" + 검색어 그대로 표시
   │     1건  → 카드로 이동
   │     N건  → **후보 목록. 시스템이 고르지 않는다**
   │
   └─ [SubstanceRef 0..N]
```

### 왜 자동 선택하지 않는가 (FQ4-6=A)

"황산"과 "황산구리"를 시스템이 골라서는 안 된다. 안전 정보에서 **잘못된 물질을
자동 선택하는 것은 R-6** 이며, 사용자는 자기가 다른 물질의 카드를 보고 있다는 것을
알 방법이 없다. 후보에는 `matched_on` 을 함께 보여 왜 걸렸는지 밝힌다.

### UN 조회 (FQ4-11=A)
경로는 존재하고 항상 0건을 돌려준다. **"지원하지 않음"이 아니라 "데이터 없음"으로
답한다** — FR-26 이 요구하는 5종 중 UN 미충족을 숨기지 않는다.

## W14. 카드 조립 (FR-24, FR-25)

```
[substance_id]
   │
   ├─ 1. 근거 문서 수집
   │     document_substance → document (+ document_section, chunk)
   │     소유자 스코프: owner_id IS NULL 만 (u5 선반영)
   │
   ├─ 2. 항목별 값 수집 — 7항목 고정 순서               (BR-102)
   │     ghs          ← MSDS 2번 섹션
   │     hp_codes     ← MSDS 2번 섹션
   │     physical     ← MSDS 9번 섹션
   │     ppe          ← MSDS 8번 섹션
   │     first_aid    ← MSDS 4번 섹션  +  물질 API 노출경로 4필드
   │     storage      ← MSDS 7번 섹션
   │     regulations  ← MSDS 15번 섹션 + 연결된 law 문서
   │
   │     ├─ **여러 출처가 있으면 전부 싣는다**            (BR-103)
   │     ├─ 본문은 그대로. 요약하지 않는다               (BR-104)
   │     └─ 각 값에 문서 제목·섹션 라벨·원문 링크        (BR-105)
   │
   ├─ 3. 결측 집계                                        (BR-106)
   │     missing_count = values 가 빈 항목 수
   │     has_msds      = subject 관계의 msds 문서 존재 여부
   │
   └─ [SubstanceCard]  — 항목 7개가 **항상** 들어 있다
```

### 항목을 감추지 않는다 (FQ4-8=A)

실측상 물질 40건 중 대부분은 MSDS 가 없어 7항목 중 6개가 빈다. 빈 항목을 빼면
**카드가 완전해 보인다.** 사용자는 "이 물질은 보호구 정보가 없다"와 "이 시스템이
보호구 항목을 안 보여준다"를 구분할 수 없다.

u2 의 BR-88(제거된 문장 개수 표시)·BR-96(단가 미등록 건수 표시)과 같은 원칙이다 —
**빠진 것이 있으면 빠졌다고 말한다.**

### 왜 응급조치만 40건 전부 채워지는가

물질 API 가 `inhale`·`skin`·`eyeball`·`oral` 을 갖고 있다. **이 유닛이 실제로 가진
유일한 폭넓은 데이터**이며, MSDS 4번 섹션이 있으면 함께 나열된다(BR-103).

### 값을 구조화 컬럼에 넣지 않는 이유

`substance.ghs_classification` 등의 컬럼은 u1 이 만들어 두었지만 **채우지 않는다.**
GHS·H/P 문구는 MSDS 본문에만 있고, 구조화하려면 2번 섹션을 파싱해 코드로 뽑아야
한다. 파싱이 어긋나면 **잘못된 GHS 분류가 구조화된 사실로** 저장된다.
본문 인용으로 보여주면 틀려도 사용자가 원문에서 확인할 수 있다.

## 실패 처리

| 지점 | 실패 | 처리 |
|---|---|---|
| 투영 (W12) | 필수 필드 전무 | 저장하지 않고 계속 진행 (BR-33). 문서 색인은 성공 |
| 투영 (W12) | 동의어 중복 | `uq_synonym_term` 으로 무시. 재색인 멱등 |
| 조회 (W13) | 0건 | 오류가 아니다. "찾지 못했습니다" + 입력값 표시 |
| 조립 (W14) | 근거 문서 0건 | 오류가 아니다. 7항목 전부 "정보 없음" + 고지 |
| 조립 (W14) | 섹션 라벨 NULL | "섹션 정보 없음" (BR-90 재사용) |

> **이 유닛에는 "정직하게 실패"할 지점이 거의 없다.** 조회 실패도 조립 실패도
> 대부분 **정상적인 결측**이며, 그것을 오류로 만들면 40건 중 33건이 오류가 된다.
> LLM 도 외부 호출도 없으므로 u2 의 폴백 층이 필요 없다.
