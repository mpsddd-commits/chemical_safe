### 스트리밍 동작 (FQ2-13, NFR-1)

```
1. 질의 전송           → "검색 중…"
2. 검색 완료            → "근거 5건 확인. 답변 생성 중…"
3. 본문 토큰 스트리밍    → 문장이 차례로 나타남 (첫 토큰 5초 목표)
4. 생성 완료 → 2단 검증  → "근거 확인 중…"
5. 검증 완료            → 인용 배지 부착, 근거 카드 표시, 제거된 문장 반영
```

**인용은 검증 후에 붙습니다.** 검증 전에 배지를 보여주면 곧 사라질 인용을 보여주게 되고,
사용자가 그 사이에 읽고 신뢰해 버립니다. 본문 스트리밍으로 체감 지연을 줄이되
인용의 정확성은 양보하지 않습니다.

| **FE-23** | 용도별·모델별 분해 | |

캐시 적중률을 표시하는 이유는 BR-94(프롬프트 배치)가 실제로 동작하는지 확인하는
유일한 방법이기 때문입니다. 0% 가 계속되면 접두사가 매 요청 깨지고 있다는 뜻입니다.

> **`verify` 가 `answer` 보다 호출 수가 많은 것은 정상입니다** (BR-86a). 2단 검증은
> 문장마다 1회 호출하므로 질의당 호출은 `1 + 문장 수` 입니다. 위 목업의 `answer 412 /
> verify 856` 이 그 비율(평균 2.1문장)입니다. 용도별 분해를 항상 노출하는 이유가
> 이것이며, **비율이 급변하면 답변 길이가 변했다는 신호**로 읽습니다.

## API 엔드포인트

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/api/query` | 질의 접수. SSE 스트림 반환 |
| `GET` | `/api/query/{id}` | 확정된 답변 + 인용 조회 |
| `GET` | `/api/usage` | 기간별 집계 (FR-42) |
| `GET` | `/api/citations/{id}/snippet` | 스니펫 단건 (인용 카드 지연 로드용). **`citation_snapshot` 을 읽는다** — `chunk` 가 아니다 (BR-92a) |

> *(2026-08-25 정정)* 이전 판은 `/api/chunks/{id}/snippet` 이었습니다. 청크를 키로 쓰면
> 재색인된 답변의 인용 카드가 404 가 되거나 **다른 문서의 본문을 보여줍니다**(청크 ID 는
> 전량 교체 시 재사용됩니다). 인용의 정체성은 청크가 아니라 인용 그 자체입니다.

### `POST /api/query` SSE 이벤트

```
event: retrieval     data: {"count": 5, "ms": 1840}
event: token         data: {"text": "분진·미스트 발생 시 "}
event: verifying     data: {"sentences": 3}
event: final         data: {"outcome":"answered_partial","sentences":[…],"citations":[…],"removed":1}
event: refused       data: {"reason":"below_threshold","links":[…]}
event: error         data: {"kind":"transient","message":"…"}
```

`final` 과 `refused` 는 상호 배타적이며 둘 중 하나는 **반드시** 전송됩니다.
클라이언트가 스트림 종료만으로 성공을 추정하면 안 됩니다.

## 접근성·표시 원칙

1. **인용 없는 문장은 화면에 나타나지 않는다** (BR-80). 예외 없음.
2. **섹션 라벨이 없으면 "섹션 정보 없음"** 이라고 쓴다 (BR-90). 빈칸으로 두지 않는다 —
   빈칸은 "정보가 있는데 로딩 실패"처럼 읽힌다.
3. **제거된 문장은 개수를 밝힌다** (BR-88). 답변이 완전해 보이게 만들지 않는다.
4. **면책 문구는 접히지 않는다** (FR-35).
5. 스니펫은 원문 그대로 표시하고 줄바꿈을 보존한다. 요약하지 않는다.
