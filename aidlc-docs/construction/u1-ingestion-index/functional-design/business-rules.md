## 1. 수집 정책 (BR-01 ~ BR-08)

| ID | 규칙 | 근거 |
|---|---|---|
| **BR-01** | `source` 가 존재하지 않거나 `enabled = false` 이면 수집 요청을 **즉시 거부**하고 작업을 생성하지 않는다 | FR-1~4 |
| **BR-02** | `requires_api_key = true` 인 소스의 인증키 환경변수가 미설정이면, **앱은 정상 기동하되** 해당 소스 수집 시도 시 "인증키 미설정: {env_name}" 오류로 즉시 실패한다. 다른 소스의 수집은 영향받지 않는다 | FQ-13=A, R-1 |
| **BR-03** | 모든 수집은 `AccessPolicyChecker` 검사를 **선행**한다. `blocked` 이면 `policy_check` 에 사유를 기록하고 **작업을 생성하지 않는다** | FR-5, CON-3 |
| **BR-04** | 정책 판정이 `blocked` 인 소스에 대해 **어떤 우회 경로도 제공하지 않는다** — 헤드리스 브라우저, User-Agent 위장, 프록시 경유 모두 금지 | CON-3 |
| **BR-05** | 정책 검사 결과는 `POLICY_CACHE_TTL`(기본 24시간) 동안 재사용한다. TTL 경과 시 재검사한다 | FR-5 |
| **BR-06** | 수집 요청 간 최소 간격 `REQUEST_INTERVAL_MS`(기본 500ms)를 준수한다. 소스별로 개별 설정 가능하다 | FR-5 |
| **BR-07** | 소스 응답의 `Retry-After` 헤더가 존재하면 그 값을 우선 적용한다 | FR-5, FR-8 |
| **BR-08** | 초기 수집 대상 물질은 **① 사고 사례에 등장한 물질 ② `is_regulated = true` 물질** 순으로 선정하며, 목표 `INITIAL_SUBSTANCE_TARGET`(기본 1,000)에 도달하면 중단한다 | FQ-14=A, SC-1 |

## 2. 변경 감지 (BR-09 ~ BR-13)

| ID | 규칙 | 근거 |
|---|---|---|
| **BR-09** | 변경 감지는 **콘텐츠 해시를 우선**한다. 기존 `document.content_hash` 와 동일하면 미변경으로 판정한다 | FR-7, FQ-9=A |
| **BR-10** | 해시 계산이 불가한 경우(스트리밍·대용량·헤더 미제공)에만 `revised_at` → `published_at` 순으로 비교한다 | FQ-9=A |
| **BR-11** | 미변경 항목은 `job_item.status = skipped` 로 기록하고 **실패로 집계하지 않는다** | FR-7, FR-8 |
| **BR-12** | 원본은 항상 보관한다 — PDF 는 파일로, API 응답은 원본 JSON/XML 로. 보관 경로는 `document.original_path` 에 기록한다 | FQ-8=A, DD-4 |
| **BR-13** | `source.last_collected_at` 은 작업 최종 상태가 `succeeded` 또는 `partial` 인 경우에만 갱신한다. `failed` 시에는 갱신하지 않아 다음 실행이 같은 범위를 재시도한다 | FR-7 |

## 4. 구조 분해 — MSDS (BR-15 ~ BR-20)

| ID | 규칙 | 근거 |
|---|---|---|
| **BR-15** | MSDS 는 **16개 표준 섹션**으로 분해한다. 섹션 코드는 `msds_01` ~ `msds_16` 이다 | FR-4, FR-9 |
| **BR-16** | 섹션 헤더 인식은 **번호 + 제목 키워드 조합**으로 판정한다. 번호 표기 변형(`1.`, `1)`, `제1항`, `Section 1`)과 제목 표기 변형을 모두 허용한다 | FR-4 |
| **BR-17** | 섹션 경계는 **다음 섹션 헤더의 시작 직전**까지다. 마지막 섹션은 문서 끝까지다 | FR-9 |
| **BR-18** | 섹션 번호가 **순서를 벗어나면**(예: 3 → 7) 건너뛴 번호는 존재하지 않는 것으로 처리하고, 인식된 섹션만 저장한다 | FR-9 |
| **BR-19** | 같은 섹션 번호가 **중복 인식되면** 첫 번째만 채택하고 나머지는 본문의 일부로 취급한다 | FR-9 |
| **BR-20** | **인식된 섹션 수가 `MSDS_MIN_SECTIONS`(기본 8) 미만이면** `structure_status = unstructured` 로 표시하고 `document_section` 행을 생성하지 않는다 | FQ-3=A, R-2 |
| **BR-20a** | *(2026-08-24 신설)* MSDS 섹션 번호가 **오름차순이 아니면** `unstructured` 로 강등한다. 2단 편집 PDF 에서 pypdf 가 오른쪽 열을 먼저 읽어 본문이 뒤섞이는데, 헤더는 정상 인식되므로 섹션 라벨이 **엉뚱한 본문에 붙는다**(실측 8건 중 2건). 틀린 인용이 인용 없음보다 나쁘다 | BR-20, NFR-8 |

## 5. 구조 분해 — 법령 및 사고사례 (BR-21 ~ BR-25)

| ID | 규칙 | 근거 |
|---|---|---|
| **BR-21** | 법령은 **조(條) 단위**로 분해한다. `제N조` 및 `제N조의M` 패턴을 인식하며, 조 제목은 괄호 안 문구로 추출한다 (`제12조(취급시설의 기준)`) | FR-2, FQ-4=A |
| **BR-22** | 항(`①②③…` 또는 `제N항`)과 호(`1. 2. 3.`)는 **별도 섹션으로 분리하지 않고** 조 청크 내부에 원문 그대로 보존한다. 조 내 항 번호 목록은 `chunk.meta.clause_numbers` 에 기록한다 | FQ-4=A |
| **BR-23** | 부칙과 별표는 **별도 섹션**으로 분리하며 `section_code` 는 각각 `부칙`, `별표N` 으로 한다 | FR-2 |
| **BR-24** | 구조 분해 단계 실패는 **파이프라인을 중단시키지 않는다.** `structure_status = unstructured` 로 표시하고 다음 단계(chunk)로 진행한다 | FQ-3=A |
| **BR-25** | 사고사례는 구조화 필드(`일시`, `유형`, `지역`, `장소`, `물질`, `원인`, `피해`, `조치`, `개요`)를 각각 섹션으로 매핑한다. 부재 필드는 섹션을 생성하지 않는다. 섹션은 **다음 라벨이 시작되는 지점까지** 이어진다(줄 단위 아님) | FR-3 |
| **BR-25a** | *(2026-08-22 개정)* 라벨은 어댑터가 산출한 **논리 필드명**을 기준으로 한다. 실제 화학사고정보 API 필드(`cscDe`, `cscTy`, `area`, `chem`, `summary`)를 그대로 내보내면 구조화기가 아무것도 인식하지 못했고, 섹션 밖 텍스트는 청킹되지 않으므로(BR-26) **사고개요 전체가 소실**되었다(169자 중 76자만 색인). 어댑터 `_project()` 가 물리 필드명을 논리명으로 변환한다 | FR-3, BR-26 |

## 6. 청킹 (BR-26 ~ BR-31a)

| ID | 규칙 | 근거 |
|---|---|---|
| **BR-26** | `structured` 문서는 **섹션 1개 = 청크 1개**를 기본으로 한다 | FQ-1=A |
| **BR-27** | 섹션의 토큰 수가 `MAX_CHUNK_TOKENS`(기본 **1,000**)를 초과할 때만 **문단 경계**로 분할한다. 분할된 청크들은 **동일 `section_id` 를 공유**하고 `ordinal` 로 순서를 유지한다 | FQ-1=A, FQ-2=A |
| **BR-27a** | *(2026-08-25 신설)* 문단 경계가 없어 분할이 불가능하면 **경계 사다리**를 내려간다 — **빈 줄 → 단일 줄바꿈 → 문장 경계 → (최후) 토큰 단위 절단**. 각 단계는 **윗 단계로 상한을 못 지킬 때만** 발동하므로 구조가 있는 문서는 영향이 없다. 잘게 나뉜 조각은 상한까지 다시 묶으므로 과분할 위험은 없다. 상한 판정은 **항상 실제 구간(`text[start:end]`)을 센다** — 조각들의 토큰 수 합이 아니다. **`MAX_CHUNK_TOKENS` 는 목표치가 아니라 불변식이다** | BR-27, DD-23 |
| **BR-28** | `unstructured` 문서는 문단(빈 줄) 경계로 누적하다가 `MAX_CHUNK_TOKENS` 초과 직전에 분할한다. `section_id = NULL` 이다 | FQ-3=A |
| **BR-29** | 청크 간 **중첩(overlap)은 두지 않는다.** 섹션·조 경계가 의미 단위이므로 문맥 손실이 작다 | FQ-2=A |
| **BR-30** | `start_offset` / `end_offset` 은 **`extracted_text.text` 기준**이며, 청크 텍스트는 반드시 이 구간과 일치해야 한다 | FQ-5=A, FR-19 |
| **BR-31** | 토큰 수가 `MIN_CHUNK_TOKENS`(기본 **20**) 미만인 청크는 **같은 섹션 안에서만** 앞 청크에 병합한다. 앞 청크가 없으면 같은 섹션의 뒤 청크에 병합한다. **섹션 경계를 넘는 병합은 금지한다.** 병합 대상이 없으면 미달이어도 단독 청크로 유지한다. *(2026-08-25 보강)* **병합 결과가 `MAX_CHUNK_TOKENS` 를 넘으면 병합하지 않는다** — BR-27a 의 상한이 우선이다 | FR-10, BR-27a |
| **BR-31a** | *(2026-08-24 신설)* 섹션 크기의 **중앙값이 `MIN_CHUNK_TOKENS` 미만**이고 문서 전체가 `MAX_CHUNK_TOKENS` 이내면, 문서 전체를 **청크 1개**로 만들고 `section_code` 는 **NULL** 로 둔다. 사고사례는 6~28토큰 필드 7개가 한 사건을 함께 서술하므로 조각내면 검색 단위가 못 된다. 반면 물질 레코드는 필드당 50~140토큰의 독립 노출경로라 그대로 둔다. 문서 종류가 아니라 **섹션 크기**로 판단하며, 여러 섹션에 걸친 청크는 특정 섹션을 주장하지 않는다(BR-31 의 라벨 보장 유지) | BR-26, BR-31 |

> **BR-31 정정 (2026-08-20, Build & Test)**: 최초 규칙은 섹션 경계를 고려하지 않아,
> MSDS 16섹션 문서가 14청크로 축소되는 결함이 단위 테스트에서 발견되었다.
> 짧은 섹션(예: 12. 환경에 미치는 영향)이 앞 섹션에 흡수되면 `section_code` 는 `msds_11` 인데
> 본문에는 12번 내용이 섞인 청크가 만들어지고, u2 가 그렇게 인용하게 된다.
> BR-31 은 BR-27 의 분할 잔여물을 정리하기 위한 규칙이지 섹션을 붙이기 위한 규칙이 아니다.

> **BR-27a 신설 근거 (2026-08-25, 실코퍼스 측정)**: BR-27 이 문단 경계를 `\n\n` 로만
> 정의했는데 이 코퍼스에는 빈 줄이 없다. 실측 1,564청크 중 **27청크가 상한 1,000토큰을 초과**했고
> 최댓값은 **8,111토큰(상한의 8배)** 이었다.
> - 법령 **부칙** — 법령 API 가 한 덩어리로 반환. 줄바꿈 **0개**, 마침표 154개
> - **msds_11**(독성정보) — 단일 줄바꿈 81개와 `○` 불릿 26개가 있는데도 빈 줄이 없어 미인식
>
> 단순한 크기 초과가 아니다. `EMBED_MAX_SEQ_LENGTH` 는 2,048 이므로 **7청크는 뒤쪽이 벡터에
> 반영되지 않은 채** 저장되었고(8,111토큰 청크는 약 75% 누락), 그런데도 BR-30 오프셋은 구간
> 전체를 가리킨다. **검색으로 도달할 수 없는 텍스트를 인용 스니펫으로는 표시하는 상태**로,
> u2 인용 신뢰성의 전제와 어긋난다. 조용히 실패한다는 점이 특히 나쁘다.
>
> 오버랩(BR-29) 재검토도 함께 수행했으나 **불필요**로 결론냈다. 분할이 실제로 발생한 섹션은
> law 26/1,110(2.3%) · msds 5/379(1.3%) 뿐이고 절단면 청크는 46개(전체의 2.9%)다.
> 나머지 97%는 섹션 경계가 곧 청크 경계라 잃을 문맥이 없다. 값 자체(1,000 / 0)는 유지한다.

> **BR-27a 보강 (2026-08-25, 재색인 실측 2회)**: BR-27a 적용 후 최댓값이 8,111 → 1,018 로
> 떨어졌으나 **15청크가 여전히 1~18토큰씩 초과**했다. 초과폭이 전부 `MIN_CHUNK_TOKENS`(20)
> 미만이어서 처음에는 BR-31 병합을 원인으로 지목했고, 그 가정으로 2차 재색인까지 돌렸으나
> **결과가 15건 그대로였다.** 가정이 틀렸다.
>
> 실제 원인은 **분할 조각을 다시 묶을 때 "조각들의 토큰 수 합"으로 판정한 것**이다.
> 청크가 저장하는 `token_count` 는 `text[start:end]` 를 센 값이고, 이 구간에는
> **조각 사이의 구분자**(공백·줄바꿈)가 포함되며 반올림도 조각마다가 아니라 한 번만
> 일어난다. 실측: 문장 39개를 합칠 때 조각 합 858 vs 실제 구간 864 — **6토큰 차이**.
> 이 간극이 15청크를 상한 너머로 밀어낸 것이다. **판정은 항상 실제 구간을 센다.**
>
> BR-31 병합에도 같은 상한 검사를 넣었다. 그쪽은 이번 15건의 원인은 아니었지만
> 동일한 방식으로 상한을 넘길 수 있는 잠재 경로이고, 두 규칙이 충돌하면 **상한이 이긴다.**
> BR-31 은 "병합 대상이 없으면 단독 유지"라는 퇴로를 이미 갖고 있어 대가가 없다.
> 짧은 청크는 검색 품질 문제지만 상한 초과는 정확성 문제다.
>
> 재색인 전 **전 코퍼스 건식 시뮬레이션**으로 검증했다: 1,598청크 / 최댓값 **999** /
> 상한 초과 **0** / BR-30 위반 0.

## 7. 메타데이터 (BR-32 ~ BR-39)

## 8. 재시도 및 오류 분류 (BR-40 ~ BR-45)

| ID | 규칙 | 근거 |
|---|---|---|
| **BR-40** | **개별 항목의 실패는 작업 전체를 중단시키지 않는다.** 다음 항목으로 진행한다 | FR-8 |
| **BR-41** | `transient` 오류(네트워크 오류, 타임아웃, HTTP 5xx, 429)는 **최대 3회** 재시도한다. 백오프는 **1초 / 4초 / 16초**, 항목당 총 대기 상한은 60초다 | FQ-10=A |
| **BR-42** | `permanent` 오류(HTTP 4xx, 텍스트 추출 불가, 스키마 불일치, 필수 메타 누락)는 **재시도하지 않는다** | FQ-11=A |
| **BR-43** | `policy_blocked` 는 **재시도하지 않으며 폴백 경로도 시도하지 않는다.** 재실행 시에도 정책 재검사가 `allowed` 로 바뀌기 전까지 해당 항목을 건너뛴다 | FQ-11=A, CON-3 |
| **BR-44** | 실패 항목은 `last_stage` 를 기록하고, 재실행 시 **그 단계부터 재개**한다. 원본이 보관되어 있으면 `fetch` 를 다시 하지 않는다 | FR-8, DD-3, FQ-8=A |
| **BR-45** | 재실행 시 이전 `permanent` 실패 항목도 **다시 시도한다** — 소스 측이 수정되었을 수 있다. `policy_blocked` 만 예외다 (BR-43) | FR-8 |

## 9. 작업 상태 (BR-46 ~ BR-52)

| ID | 규칙 | 근거 |
|---|---|---|
| **BR-46** | 작업 상태는 **자체 `job` / `job_item` 테이블**로 관리하며, 큐 백엔드의 결과 저장소에 의존하지 않는다 | DD-13 |
| **BR-47** | 수집·색인 요청은 작업을 생성하고 큐에 등록한 뒤 **즉시 `job_id` 를 반환**한다. 요청 스레드에서 처리하지 않는다 | FR-6 |
| **BR-48** | 작업 최종 상태 판정: 실패 0건 → `succeeded` / 성공 ≥ 1 이고 실패 ≥ 1 → `partial` / 성공 0건이고 실패 ≥ 1 → `failed` | FQ-12=A |
| **BR-49** | **전건이 `skipped`(변경 없음)인 작업의 최종 상태는 `succeeded`** 다. 실패로 판정하지 않는다 | FR-7, FQ-12=A |
| **BR-50** | 진행률 = `(success_count + skipped_count + failure_count) / total_count`. `total_count = 0` 이면 0% 로 표시한다 | FR-6, FR-48 |
| **BR-51** | 재실행은 **새 작업을 생성**한다. 기존 작업의 상태와 이력은 변경하지 않는다 | FR-6 |
| **BR-52** | 워커는 `WORKER_HEARTBEAT_INTERVAL`(기본 30초)마다 하트비트를 갱신한다. 마지막 하트비트가 `WORKER_STALE_THRESHOLD`(기본 120초)를 초과하면 헬스체크에서 `worker` 를 비정상으로 보고한다 | FR-43 |

## 11. 로깅 및 보안 (BR-57 ~ BR-60)

| ID | 규칙 | 근거 |

| **BR-57** | 모든 로그는 **구조적 JSON** 형식이며, `request_id`(또는 `job_id`)로 처리 경로 전체를 상관 추적할 수 있어야 한다 | FR-40 |

> **BR-59 정정 (2026-08-20, Build & Test)**: 최초 구현은 키 이름에 `token` 이 포함되면 마스킹했는데,

| **BR-60** | `job_item.failure_reason` 및 오류 로그에 포함되는 URL·헤더는 **비밀값을 마스킹한 뒤** 저장한다 (쿼리 파라미터의 `key`, `token`, `apikey` 등) | NFR-14 |
